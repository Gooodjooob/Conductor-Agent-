# 案例四：离线通过后仍拒绝宣布接入

> 关键词：入口门 / 证据分级 / ENTRY_UNVERIFIED

## 问题

协议与回传的**离线测试全部通过**，看起来可以宣布"DSH 接通了"。但真实入口还依赖插件、native 包、动态 profile 和构建来源——离线通过不能证明这些。

## 关键动作

按**真实入口**逐项核对：

- source / build / lock 的对应关系
- 依赖图、平台包与 loader
- 区分 requested 模型与 observed 模型
- 区分「请求的身份」与「实际观察到的身份」

**缺任何一项，保持 ENTRY_UNVERIFIED 状态，不上调结论等级。**

## 结果与证据

| 记录 | 状态 | 说明 |
|---|---|---|
| D2 | 阶段限定离线批准 | 636 tests + 70 public probes 通过，但**仅限离线链路** |
| D1 | 真实入口审核 | 识别出未闭合项：真实 DSH、模型、OS canary、通知和双轮未运行 |

⚠️ **636 tests 与 70 probes 不用来证明生产通过。** 这是刻意保留的表述边界。

## 取舍

**保留阻塞状态，而不绕开入口门。** 宁可进度看起来慢，也不把离线成功外推为"真实接入完成"——因为一旦对外宣布接通，后续问题会以"你不是说接通了吗"的形式反噬信任。

## 追问准备

| 追问 | 回答要点 |
|---|---|
| 模型名称一致能否证明身份？ | 不能。requested 与 observed 分开记录，名称一致只是必要条件 |
| lexical scanner 与完整模块解析有什么区别？ | 词法扫描只能看到表面字符串，完整解析才能确认模块真实加载路径 |
| source/build 关联为何不等于构建 attestation？ | 有关联只说明"构建时参考了这份源码"，不证明产物由它构建且未被篡改 |
