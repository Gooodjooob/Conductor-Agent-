# 案例一：从重复传话到可追溯交付

> 关键词：task/attempt 建模 / 真实双轮 / 冻结输入

## 问题

销售助手的开发分散在多个 Agent 和宿主（Codex、WorkBuddy、Trae、QClaw）中，出现三个反复发生的问题：

1. 对话交接不稳定，任务转手时目标丢失
2. 返工会覆盖历史报告，审核无法对应具体版本
3. 平台返回「提交成功」，却无法证明宿主真的接收并执行了

## 承担工作

定义控制面的范围与四层模型：**task（任务）→ attempt（执行轮次）→ delivery（交付物）→ review（审核）**，并优先打通指定成员的一条真实垂直切片。

## 关键动作

- 用 task 保存稳定目标，用 attempt 保存一轮执行
- 冻结任务卡、宿主与输入版本，保证两轮之间可对比
- Adapter 处理宿主提交，控制服务写执行事实，看板只读
- 返工时新建 attempt，旧交付保留可查，不覆盖历史

## 结果与证据

2026-10-01 在 QClaw 上完成真实双轮验证：

1. 首轮交付 → 主控要求返工
2. 新一轮 attempt 交付 → 主控审核通过
3. **两轮文件独立保留**，审核结论绑定具体轮次

⚠️ 当时的回执是**人工核验后导入**的，没有包装成全自动调度。

## 取舍

先把「交付追溯」做实，**延后自动选人、抢占、费用路由和全局调度**。理由：可独立观察的纵向场景先跑通，再扩调度复杂度。

## 追问准备

| 追问 | 回答要点 |
|---|---|
| 为什么不能只用一个 task.status？ | 审核必须对应"这一轮的输入、环境、产物版本与审核者"，任务级状态无法承载多轮历史 |
| 返工后旧交付如何审核？ | 旧 delivery 保留但标记非当前；审核要求当前 delivery，changes_requested 生成新 attempt |
| 如何知道宿主真的接收？ | 提交 / 接收 / 开始 / 交付 / 入账 / 审核六段分开记录，缺任何一段都显示为未知而非成功 |
