# 案例二：超时后先恢复事实再决定重试

> 关键词：unknown 一等公民 / 恢复对账 / 幂等与冲突

## 问题

runner 退出或预算耗尽时，可能**文件已经产生了，但没有正式交付**。直接重派会重复修改或覆盖产物；当作"没发生过"同样错误。

## 关键动作

1. **区分六个阶段**：提交、接收、开始、交付、入账、审核。任何一段缺失都不等于整体失败或整体成功
2. **保留 unknown**：超时且无正式交付的轮次记为 UNKNOWN_SUBMIT，不直接改数据库补 accepted
3. **对账优先**：核对进程、源码、原始回执与数据库，确认"旧操作发生了什么"，再决定补采集、修复还是新执行
4. **幂等三合一**：
   - 同 eventId 同内容 → 返回首次结果
   - 同 eventId 不同内容 → 拒绝并留冲突记录
   - 校验轮次、序号与终态，迟到事件不得回退当前终态；关键状态判断在写事务内复读

## 结果与证据

- L0、W1 保留了 UNKNOWN_SUBMIT 与「超时且无正式交付」的历史记录
- C1（事件服务）可定位 ingest、_ingest_locked、_replay 等去重与冲突处理流程
- C2（审核服务）拒绝审核旧版本交付，changes_requested 生成新 attempt

⚠️ 本轮为静态代码核对，未重新运行测试套件。

## 取舍

恢复流程多了一步对账，换来的是**避免对未知副作用盲目重放**。不承诺分布式 exactly-once——幂等只在单服务事务边界内成立，跨文件 / SQLite / 宿主不做原子事务保证。

## 追问准备

| 追问 | 回答要点 |
|---|---|
| 同 eventId 不同 payload 怎么办？ | 拒绝写入并留冲突记录，不静默覆盖；冲突暴露出来让人裁决 |
| 旧 attempt 的迟到终态怎么办？ | 校验轮次与序号，终态已推进则拒绝回退，在事务内复读当前状态 |
| 通知失败为何不生成新 attempt？ | 业务完成、审核、消息送达、发布是四个独立事件；通知恢复是补偿消息，不是重新开发 |
| 文件与 SQLite 不一致怎么办？ | 以对账结果为准标记产物归属，按明确范围和新身份承接，不做隐式合并 |
