# 案例三：看板刷新正确性与交互连续性

> 关键词：只读投影 / 变化检测 / UI 稳定性

## 问题

原看板每 5 秒无条件重建 DOM，带来三个副作用：

1. 用户阅读时页面闪动
2. 滚动位置和焦点丢失
3. 项目路径与执行角色展示不完整

## 关键动作

1. **只读核对**：每 30 秒从登记来源读取，与当前渲染状态比对，**仅在数据变化时重新渲染**
2. **状态保持**：重新渲染时保留滚动位置、焦点、展开状态与弹窗
3. **信息补全**：补充项目源码、卡片和报告路径；区分「指定执行者」「实际身份」「QA」「审核者」四类角色
4. **不自动入账**：其他项目文件变化只提示复核，不凭文档 PASS 自动验收

## 结果与证据

B1 记录的回归范围（54 项，来源/路径/角色/刷新修复）：

| 指标 | 结果 | 限定范围 |
|---|---|---|
| 无变化时删除节点数 | 0 | 指定 UI 场景 |
| 变化后滚动位置 | 300 → 300 | 指定 UI 场景 |
| 焦点保留 | 是 | 指定 UI 场景 |

⚠️ 以上不代表全设备零闪烁或全场景性能指标。本轮修复归属主控直接修复，未伪装为 worker 交付。

## 取舍

**降低刷新频率（5s → 30s）以换取稳定阅读**，同时保留手动刷新和重新打开后的来源读取。数据的实时性让位于阅读连续性——因为看板的定位是"只读证据展示"，不是实时监控。

## 追问准备

| 追问 | 回答要点 |
|---|---|
| 如何区分"无变化"？ | 对比登记来源的结构化读回状态与当前渲染状态，结构相同则跳过渲染 |
| 刷新出错怎么办？ | 刷新失败保留上一次渲染结果并提示，不白屏、不清空 |
| 为什么页面关闭后不继续采集？ | 看板是只读投影，采集责任在控制服务侧的登记机制，页面只负责展示 |
| 当前版本和历史 approved 如何隔离？ | 审核绑定当前 delivery，历史 approved 记录保留但不参与当前状态判断 |
